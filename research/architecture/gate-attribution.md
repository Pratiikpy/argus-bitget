# Gate attribution: which check refused, and which never ran

**Question this teardown answers.** Across a log of decisions, how do the best systems record *why*
nothing happened — and do any of them distinguish a gate that **evaluated and allowed** from a gate
that **never executed** because an earlier one returned first?

**Answer: none of the four do.** Three do not track it at all; the one that appears to
(`vibe-trading`) records a hardcoded list that is identical whether the first gate refused or the
twelfth did. This is the gap ARGUS's `eval/autopsy.py` closes.

All file:line references below were opened and read, not taken from a search summary.

---

## 1. `nautechsystems/nautilus_trader` — the best refusal taxonomy in the corpus

`research/repos-t2/nautechsystems~nautilus_trader/crates/model/src/events/order/denied_reason.rs`
(1,059 lines).

`OrderDeniedReason` (`:69`) is a Rust enum of **37 struct variants**, each carrying typed context
rather than a formatted string, with the display form generated by `#[error(...)]`:

```rust
pub enum OrderDeniedReason {
    #[error("PRICE_PRECISION_EXCEEDS_MAXIMUM: field={field}, price={price}, ...")]
    PricePrecisionExceedsMaximum {
        field: OrderPriceField,
        price: Price,
        price_precision: u8,
        max_precision: u8,
    },
```

**What we take.** The principle that a refusal reason is a *typed value with its comparison operands
attached*, not a sentence. `QUANTITY_EXCEEDS_MAXIMUM: effective=15, max=10` can be aggregated,
filtered and diffed; "position too large" cannot. Our `GateOutcome` carries `reached` and `fired`
counts beside the gate's own description for the same reason.

**What it does not do.** The denial event records the reason that fired and nothing about the rules
that did not. The ordering is implicit in the control flow of the risk engine, so from a corpus of
denial events you can count how often each reason fired but you **cannot** tell whether a reason
with zero occurrences is permissive or unreachable. For a risk engine this matters: an unreachable
check is dead code wearing the appearance of a safeguard.

## 2. `hkuds/vibe-trading` — the closest attempt, and it is wrong in a specific way

`research/repos-t2/hkuds~vibe-trading/agent/src/live/sdk_order_gate.py` (1,116 lines).

This is the only implementation in the corpus that tries to record *which gates were consulted*. The
decision envelope carries a `checked_limits` list beside the allow/deny decision (`:398`, `:418`,
`:493`, `:514`):

```python
gate_decision={
    "allowed": True,
    "decision": _DECISION_ALLOW,
    "checked_limits": checked,
},
```

and `checked` is built at `:283`:

```python
checked = [
    "mandate", "expiry", "halt_flag", "exclude_symbols", "allowed_instruments",
    "asset_classes", "max_order_notional_usd", "max_total_exposure_usd",
    "max_leverage", "max_trades_per_day", "account_funding_usd", "universe_floors",
]
```

**The defect, verified rather than inferred.** `checked` is assigned as a static literal at `:283`,
`:469` and `:544` and is **never mutated** — `grep` for `checked.append` / `checked.remove` /
reassignment returns only those three assignments and one expression-level `checked + [...]` at
`:681`. So an order denied by the **first** gate is recorded as having had all **twelve** limits
checked. The field reads like reachability evidence and is a constant.

This is worse than not recording it. A reviewer reading `checked_limits` reasonably concludes those
twelve rules were exercised; the log cannot support that for any denied order.

**What we take.** The idea of carrying the consulted set in the decision envelope. **What we
reject:** a statically declared set. Ours is derived by walking the chain in source order and
subtracting what each gate took, which is the same short-circuit the policy itself performs.

## 3. `freqtrade` — honest, minimal, no attribution

`research/corpus/repos/freqtrade/freqtrade/plugins/protections/iprotection.py:17-22` defines
`ProtectionReturn` with a plain `reason: str | None`. `ProtectionManager` iterates the configured
protections and returns on the first that locks.

No reason taxonomy, no codes, and no record of the protections that did not fire. It does not claim
otherwise, which makes it more honest than §2 even though it records strictly less.

---

## 4. `minihellboy/factorminer` — typed context, single reason

`research/repos-t2/minihellboy~factorminer/factorminer/evaluation/admission.py:21-85`.
`AdmissionDecision` carries `rejection_reason: str | None` plus the operands that produced it
(`max_correlation`, `correlated_with`), giving reasons like
`"Too correlated: max|rho|=0.62 >= 0.5 (with F-123)"` (`:71-74`).

Good on context, silent on sequence: one reason, the one that fired, no notion of what came before
or after it.

## What ARGUS does instead

`argus/src/argus/eval/autopsy.py`.

1. **Three states, not two.** `FIRED`, `PASSED`, `UNREACHED`. Every system above collapses the last
   two into "did not fire", which is the error: "the confidence floor allowed 170 decisions
   through" and "the confidence floor was never evaluated" support opposite conclusions.

2. **Reachability derived, never declared.** `CHAIN` records the Constitution's rules in source
   order (`argus/src/argus/agents/desk.py:651-700`) and `examine()` walks it, subtracting each
   gate's hits from the live population before considering the next — reproducing the early-return
   structure of the policy. Nothing is asserted about what was consulted; it is computed from what
   bound. This is the specific fix for §2's static list.

3. **Aggregate funnel over a whole log**, which none of the four produce. Nautilus counts denial
   events; nobody reports per-gate survival across a corpus of decisions.

4. **A stated falsifier.** The autopsy concludes that ARGUS's abstentions are explained by session
   coverage rather than by the desk, and prints the observation that would refute it (one cycle with
   price discovery in which the desk still proposes nothing) together with how many hours away that
   observation is. None of the four attaches a falsifier to its own conclusion, because none of them
   draws one — they report reasons, not causes.

**Where they are still ahead.** Nautilus's 37 typed variants are a far richer taxonomy than our five
gates, and if ARGUS's Constitution ever grows past a handful of rules the string-keyed
`binding_constraint` should become a typed enum on the Nautilus model. Noted rather than done: with
five rules, an enum would be ceremony.
